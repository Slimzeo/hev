Go Core 保持一条直接的调用链：

```text
cmd/hev/main.go
  -> internal/handler/command.go
  -> internal/domain/environment/service.go
  -> internal/dal/json/environment.go

internal/handler/command.go
  -> internal/packer/response.go
```

各文件职责固定如下：

| 文件 | 职责 |
| --- | --- |
| `cmd/hev/main.go` | 启动进程并组装 Store、Service 与 Handler |
| `internal/handler/command.go` | 解析 Cobra 命令和参数，调用 Environment Service |
| `internal/domain/environment/model.go` | 定义 Environment、Skill policy、校验和数字状态错误 |
| `internal/domain/environment/service.go` | 实现 Environment 用例，并声明这些用例需要的最小 Store 接口 |
| `internal/dal/json/environment.go` | 实现 Store，负责文件锁、JSON 读写和原子替换 |
| `internal/packer/response.go` | 将领域结果或错误转换为 CLI v2 JSON |
| `contracts/cli/v2/` | 保存跨进程 JSON Schema 与 fixtures |
| `test/hev_test.go` | 集中保存 Go Core 测试 |

`Store` 接口与 Service 放在 `service.go`，因为它描述 Service 需要什么；`dal/json` 只负责实现它。Go Core 不增加独立 application 层，也不把持久化实现放进 domain。

## 三、模型设计

### 3.1 Skill关键 domain model

1. `SkillKey`
   hev Core 对一个逻辑 Skill 的稳定标识，不等同于 DSH、OpenCode 等宿主的原生对象。MVP 默认使用相同名称映射，但 Core 不导入任何宿主 Skill 类型。

   ```go
   type SkillKey string
   ```

2. `EnvironmentSkillSpec`
   抽象一个 Environment 如何使用某个 Skill。
   hev 只保存逻辑 key，不复制 Skill 正文、物理路径或 Provider 私有 locator。

   ```go
   var skill_key SkillKey
   var policy EnvironmentSkillPolicy
   ```

3. `EnvironmentSkillPolicy`
   抽象 Skill 在一个具体 Environment 中的调用策略。
   这是 Environment 与 Skill 的关系属性，不是 Skill 自身的全局属性。

   ```go
   // auto | off
   var kind string
   ```

   MVP 只支持 `auto` 与 `off`。current Environment 中只有 `auto` Skill 可见；`off` 与未列入的 Skill 均不可见。

### 3.2 Environment关键domain model



1. `EnvironmentId`
   Environment 的稳定唯一标识。Go Core 使用自有类型，避免与普通字符串混用。

   ```go
   type EnvironmentId string
   ```

2. `Environment`
   hev 的核心领域实体，只描述环境本身及其 Skill 配置，不保存当前是否被 Session 使用，也不保存宿主路径。

   ```go
   var id EnvironmentId
   var name string
   var revision uint64
   var skills []EnvironmentSkillSpec
   ```

   `revision` 是 Go Store 当前记录的元数据，由创建和更新操作维护。它不表示可选历史版本；`hev env use` 每次返回最新 Environment，MVP 不使用 `revision` 选择、锁定或回退版本。

### 3.3 Store与Runtime model

1. `EnvironmentStore`
   Environment 当前记录的持久化接口，定义在 `internal/domain/environment/service.go`，由 `internal/dal/json/environment.go` 实现。MVP 不为字段完全相同的数据额外公开 `EnvironmentRecord`。

   ```go
   Create(ctx context.Context, environment Environment) (Environment, error)
   GetByIDOrName(ctx context.Context, identifier string) (Environment, error)
   UpdateMany(ctx context.Context, identifiers []string, mutate func([]Environment) error) ([]Environment, error)
   ```

   MVP 每个 `EnvironmentId` 只保存一份当前记录，`GetByIDOrName` 只返回一个 Environment 的当前值。`UpdateMany` 仅服务于批量 `skill add --env ...` 配置写入，不表达 active Environment 组合。`dal/json.EnvironmentStore` 在创建时写入初始 revision、更新时自行递增，并负责文件锁、原子替换和持久化 JSON 校验。

2. `EnvironmentController`
   `@slimzeo/hev-dsh-plugin/hev-runtime` 入口导出的 Service。`use()` 将调用方给出的单个 Environment ID 或名称传给 Go CLI；CLI 返回值通过 [JSON v2](../contracts/cli/v2/) 校验后，从 `data.environment` 取得规范化 `EnvironmentId`，写入以精确 live DSH `Session` 对象为键的 `WeakMap`。`current(session, signal)` 使用保存的 ID 再次调用 CLI，返回最新 Environment。
   该入口不替代 DSH 的 `AgentRegistry`、`SessionStore` 或 `SkillRegistry`，也不把选择状态写入 Go Store；同一公开包的 `hev-skill-registry` 入口另行以兼容子类替换基础 `ctx.skills` 实现。

   ```typescript
   export default class EnvironmentController extends Service {
     private readonly environmentIdBySession = new WeakMap<Session, EnvironmentId>()

     current(session: Session, signal?: AbortSignal): Promise<Environment>
     use(agent: Agent, environmentRef: string, signal?: AbortSignal): Promise<Environment>
   }
   ```

   `use(agent, environmentRef, signal)` 使用传入 Agent 的精确 live `Session` 作为键。`current(session, signal)` 必须使用同一个 `Session` 对象查询；没有显式选择时执行无 Environment 参数的 CLI `use`，由 Core 返回默认 Environment；有选择时按保存的规范 ID 重新执行 CLI `use`，并将返回的规范 ID 写回该 Session。因此外部更新 Environment 后，下一次读取会得到最新内容；`revision` 不参与版本选择。`WeakMap` 只表达当前进程内对象生命周期。

### 3.4 DSH Adapter复用与扩展的model

1. `SkillInvocationPolicy`
   直接复用 `@deepseek-ai/dsh-skill` 的调用入口策略。它只表示模型和用户两个入口是否允许调用，不表示 hev 的自动触发频率。

   ```typescript
   interface SkillInvocationPolicy {
     readonly modelInvocable: boolean
     readonly userInvocable: boolean
   }
   ```

   复用原因：`dsh-tool-skill` 已经在 catalog、`skill` Tool 和用户 `/name` 入口执行这套策略。hev 不复制这两个布尔字段；精确 live Agent 的 current Environment 中，`HevSkillRegistry` 只保留 `policy.kind === 'auto'` 且被 Environment 列入的 Skill，`off` 与未列入的 Skill 均不可见；保留下来的 Skill 继续使用原生 invocation 值。

2. `SkillSummary`、`SkillResourceBase` 与 `SkillCandidate`
   直接复用 `@deepseek-ai/dsh-skill` 的 Skill 摘要、资源基址与候选模型。Provider 用 Candidate 做轻量发现，Registry 用 `rank`、Provider 注册顺序和本地顺序完成同名决胜；对外列表只暴露去掉 `rank` 和 `locator` 的 Summary。

   ```typescript
   type SkillSource =
     | 'project-dsh'
     | 'project-agents'
     | 'runtime'
     | 'user-dsh'
     | 'user-agents'
     | 'custom'
     | 'bundled'
     | (string & {})
   
   type SkillResourceBase =
     | { readonly kind: 'directory'; readonly path: string }
     | { readonly kind: 'url'; readonly url: string }
     | { readonly kind: 'opaque'; readonly description: string }
   
   interface SkillSummary {
     readonly name: string
     readonly description: string
     readonly whenToUse?: string
     readonly invocation: SkillInvocationPolicy
     readonly source: SkillSource
     readonly provider: string
     readonly resourceBase?: SkillResourceBase
   }
   
   interface SkillCandidate extends SkillSummary {
     readonly rank: number
     readonly locator: unknown
     readonly path?: string
     readonly metadata?: Readonly<Record<string, unknown>>
   }
   ```

   复用原因：hev 只决定当前 Session 是否允许这个 Candidate，不能取代 Provider 的发现、排序和 locator 解释。`locator` 只留在 DSH Adapter 内，不写入 hev Core 或 JSON。

3. `SkillDefinition`
   直接复用 `@deepseek-ai/dsh-skill` 的完整 Skill 模型，由获胜 Candidate 的原 Provider 延迟加载。

   ```typescript
   interface SkillDefinition extends SkillSummary {
     readonly content: string
     readonly path?: string
     readonly metadata?: Readonly<Record<string, unknown>>
   }
   ```

   复用原因：Skill 正文可能来自本地文件、runtime registration、bundled package 或远端 Provider。hev 不复制正文，就不会出现两份 Skill 数据和两套失效规则。

4. `SkillProvider` 与 `SkillRegistry`
   `@slimzeo/hev-dsh-plugin/hev-skill-registry` 继承 DSH 的 `SkillRegistry`，不新建第二套 `SkillManagement`。Provider 注册、scope 合并、winner 选择、校验和正文加载继续由父类负责。以下是它复用的现有 public surface。

   ```typescript
   interface SkillLookupOptions {
     readonly cwd?: string
     readonly signal?: AbortSignal
   }
   
   interface SkillProviderObservation {
     readonly candidates: readonly SkillCandidate[]
     readonly complete: boolean
   }
   
   interface SkillProvider {
     readonly name: string
     readonly list: (options: SkillLookupOptions) => Promise<readonly SkillCandidate[] | SkillProviderObservation>
     readonly get: (candidate: SkillCandidate, options: SkillLookupOptions) => Promise<SkillDefinition | undefined>
   }
   
   interface SkillProviderControl {
     readonly signal: AbortSignal
     readonly invalidate: () => void
   }

   interface SkillViewOptions extends SkillLookupOptions {
     readonly scope?: ScopeKey
   }
   
   class SkillRegistry extends Service {
     registerProvider(create: (control: SkillProviderControl) => SkillProvider): () => void
     list(options?: SkillViewOptions): Promise<SkillSummary[]>
     snapshot(options?: SkillViewOptions): Promise<SkillCatalogSnapshot>
     get(name: string, options?: SkillViewOptions): Promise<SkillDefinition | undefined>
   }
   
   interface SkillCatalogSnapshot {
     readonly skills: SkillSummary[]
     readonly complete: boolean
   }
   ```

   `HevSkillRegistry` 先调用父类完成原有 rank、Provider 顺序和 scope shadowing，再过滤结果。它只 override `snapshot()` 与 `get()`；父类 `list()` 动态调用 `this.snapshot()`，因此会进入 override，无需重复实现。只过滤 `dsh-tool-skill` 或 `skill-filesystem` 都不能形成隔离。

5. `Session`
   `hev-runtime` 入口直接使用 DSH 的精确 live `Session` 对象；`HevSkillRegistry` 先从现有 `SkillViewOptions.scope` 找到精确 live Agent，再使用它的 `agent.session`。

   ```typescript
   const environmentIdBySession = new WeakMap<Session, EnvironmentId>()
   ```

   复用原因：对象身份就是 MVP 的隔离键。Session ID 或另一个 `Session` 对象都不能替代原对象命中这份状态；对象不可达后，`WeakMap` 允许运行时状态随之回收。

6. `Agent` 与 `SkillViewOptions.scope`
   hev 不修改 `SkillViewOptions`。`HevSkillRegistry` 用 `options.scope` 与 `ctx.agents.list()` 返回值做精确对象匹配；相同 ID 的另一个对象或任意其他 scope 都不算 live Agent。

   ```typescript
   const agent = options.scope === undefined
     ? undefined
     : ctx.agents.list().find(candidate => candidate === options.scope)
   ```

   找不到精确 Agent 时直接返回父类原生 view；找到后调用 `ctx.environment.current(agent.session, options.signal)`。该 Session 没有显式选择时，`current()` 返回默认的 `base` Environment，不回退到原生 view。

7. `HevSkillRegistry`
   `@slimzeo/hev-dsh-plugin/hev-skill-registry` 默认导出 `HevSkillRegistry extends SkillRegistry`，并继续提供同一个 `ctx.skills` service。它不是并行 Registry，也不要求 DSH 新增 API。

   ```typescript
   export class HevSkillRegistry extends SkillRegistry {
     static inject = ['agents', 'environment']

     override async snapshot(options: SkillViewOptions = {}): Promise<SkillCatalogSnapshot> {
       const catalog = await super.snapshot(options)
       const allowed = await this.allowedSkillNames(options)
       if (allowed === undefined) return catalog
       return { ...catalog, skills: catalog.skills.filter(skill => allowed.has(skill.name)) }
     }

     override async get(name: string, options: SkillViewOptions = {}): Promise<SkillDefinition | undefined> {
       const allowed = await this.allowedSkillNames(options)
       if (allowed !== undefined && !allowed.has(name)) return undefined
       return await super.get(name, options)
     }

     private async allowedSkillNames(options: SkillViewOptions): Promise<ReadonlySet<string> | undefined> {
       const agent = options.scope === undefined
         ? undefined
         : this.ctx.agents.list().find(candidate => candidate === options.scope)
       if (agent === undefined) return undefined
       const environment = await this.ctx.environment.current(agent.session, options.signal)
       return autoSkillNames(environment)
     }
   }
   ```

   `autoSkillNames()` 只收集 current Environment 中 `policy.kind === 'auto'` 的 `skillKey`。`off` 与未列入的 Skill 都不进入 allow-set。`snapshot()` 过滤父类已选出的 Summary；`get()` 在调用父类加载正文前执行相同判断。

8. 单一发布包与两个 Cordis 入口
   对用户只发布一个聚合包 `@slimzeo/hev-dsh-plugin`。其 `/hev-runtime` subpath 默认导出 `EnvironmentController` 并注册 `ctx.environment`；`/hev-skill-registry` subpath 默认导出 `HevSkillRegistry`，替换基础 `skill` Plugin 后仍注册同一个 `ctx.skills`。这是两个运行时职责，不是三个需要分别安装的 npm 包。

   ```yaml
   - id: skill
     name: '@deepseek-ai/dsh-skill'
     disabled: true

   - insert:
       - id: hev-runtime
         name: '@slimzeo/hev-dsh-plugin/hev-runtime'
       - id: hev-skill-registry
         name: '@slimzeo/hev-dsh-plugin/hev-skill-registry'
   ```

   bundle 必须先禁用 base 中 `id: skill` 的原生实例，再按依赖顺序插入 `hev-runtime` 和 `hev-skill-registry`；不能同时挂载两个提供 `ctx.skills` 的 Service。包中同时携带支持平台的预编译 `hev`，`hev-runtime` 默认通过自身 `import.meta.url` 解析，不依赖用户 PATH；`executable` 仅作为开发和测试覆盖项。

### 3.5 复用边界与跨宿主迁移

复用 DSH model 的确会让 **DSH Adapter** 依赖 DSH，但这是 Adapter 的职责，不等于 hev Core 与 DSH 耦合。依赖方向固定为：

```text
hev Core（SkillKey / Environment / Policy）
    ↑
    ├── DSH Adapter（SkillCandidate / SkillDefinition / Session）
    └── OpenCode Adapter（OpenCode native skill / session model）
```

hev Core 不导入 Cordis、DSH `Session`、`ScopeKey`、`SkillCandidate` 或 `locator`。迁移到 OpenCode 时保留 Environment JSON、CLI 用例和 policy 解析，只新增 OpenCode Adapter，将 `EnvironmentSkillSpec.skill_key` 映射到 OpenCode 的原生 Skill name。MVP 可约定逻辑 key 与各宿主原生 name 相同；若名称不同，映射只进入对应 Adapter 配置。如果 OpenCode 没有 Registry 过滤扩展点，Adapter 需要使用它支持的受控 Skill root 或启动配置实现隔离；不把该差异反向塞进 Core。

## 六、存储层设计
MVP 暂定只使用 JSON 持久化 hev 自有的 `Environment`。Skill 的发现、正文和物理位置继续由各宿主的原生 Skill Provider 管理；hev 不保存第二份 `skills.json`。

### 6.1 Environment Store

`$HOME/.hev/environments.json`

```json
{
  "schemaVersion": 1,
  "environments": [
    {
      "id": "env_base",
      "name": "base",
      "revision": 1,
      "skills": []
    }
  ]
}
```

`policy.kind` 取值为 `auto` 或 `off`。`dal/json.EnvironmentStore` 是 domain `Store` 接口的第一版实现。

当存储文件不存在或 `environments` 是空数组时，JSON Store 自动持久化上述普通空 `base` 记录。`base` 没有特殊字段或版本规则；它是 DSH live Session 未显式 `use` 时采用的默认 Environment。

### 6.2 DSH live Session 状态

DSH Adapter 持有 `WeakMap<Session, EnvironmentId>`；`use(agent, name)` 调用 Go CLI，完整解析并校验返回值后，从 `data.environment` 提取规范 ID，并替换该精确 `agent.session` 的唯一条目。`current(session, signal)` 没有条目时调用无 Environment 参数的 CLI `use`，由 Core 决定默认 Environment；有条目时使用保存的规范 ID。两条路径都返回最新 `Environment`，并写回返回的规范 ID。

这份状态只属于当前进程和当前 `Session` 对象。不同的 `Session` 对象即使 ID 相同，也各自使用自己的选择；没有显式选择的对象使用 `base`。

## 七、CLI 与 Plugin 契约

`@slimzeo/hev-dsh-plugin/hev-runtime` 通过子进程调用包内 `hev` CLI，复用 Go Core 的 Environment use case，并把成功返回的规范 Environment ID 写入当前 live `Session` 对应的 `WeakMap` 条目。`@slimzeo/hev-dsh-plugin/hev-skill-registry` 用替换后的 `HevSkillRegistry` 管理 Skill 可见性；根包的 bundle manifest 只负责安装顺序与配置。未来接入 OpenCode 时复用同一 CLI 与 JSON，只替换宿主 Adapter。

### 7.1 调用规则

- Plugin 调用 CLI 时固定传入 `--output json`。
- `stdout` 只输出一个 JSON 对象，`stderr` 只输出日志和诊断信息。
- 成功时退出码为 `0`，失败时为非 `0`；失败时 `stdout` 仍返回结构化错误。
- Plugin 必须先校验 `schemaVersion` 和 JSON 结构，再使用返回数据。

### 7.2 公共返回结构

成功：

```json
{
  "schemaVersion": 2,
  "code": 200,
  "message": "success",
  "prompt": "",
  "data": {}
}
```

失败：

```json
{
  "schemaVersion": 2,
  "code": 404,
  "message": "environment not found: coding",
  "prompt": "create the environment before using it",
  "data": {}
}
```

`code` 是唯一公开的错误分类，也是 Go domain error 携带的数值 `StatusCode` 在 wire 上的原值：`400` 表示参数错误，`404` 表示 Environment 不存在，`409` 表示已有配置冲突，`500` 表示内部错误。`message` 用于说明失败，`prompt` 提供下一步提示，所有失败响应的 `data` 都是空对象。

#### 注册 Skill 并加入 Environment

```bash
hev skill add <skill-key> --env <env-name> [--env <env-name>...] [--policy <auto|off>] --output json
```

```json
{
  "schemaVersion": 2,
  "code": 200,
  "message": "skill added to environment",
  "prompt": "",
  "data": {
    "environmentSkill": {
      "skillKey": "code-review",
      "policy": {
        "kind": "auto"
      }
    },
    "environments": [
      {
        "id": "env_01",
        "name": "coding",
        "revision": 2
      }
    ]
  }
}
```

MVP 传入的是 hev `skill-key`，CLI 只在指定 Environment 中写入 `EnvironmentSkillSpec`，不复制 Skill 正文或物理路径。MVP 只接受 `--policy auto|off`。DSH Adapter 将 `skill-key` 等值映射为原生 Skill name；`HevSkillRegistry` 在 `snapshot()` 与 `get()` 读取时与原生 winner 求交集，找不到原生 Skill 的 key 保持不可见，但不阻止 `use`。

#### 使用 Environment

```bash
hev env use [env-id-or-name] --output json
```

```json
{
  "schemaVersion": 2,
  "code": 200,
  "message": "environment resolved",
  "prompt": "",
  "data": {
    "environment": {
      "id": "env_01",
      "name": "coding",
      "revision": 2,
      "skills": [
        {
          "skillKey": "code-review",
          "policy": {
            "kind": "auto"
          }
        }
      ]
    }
  }
}
```

CLI 接受零个或一个 ID/名称；省略时由 Core 返回默认 Environment，显式传值时读取该 Environment，并在 `data.environment` 返回它。`revision` 不参与版本选择。Core 校验 Environment 与 policy；Environment 不可用时 CLI 失败。`EnvironmentController.use()` 只在 CLI 成功后替换该 Session 的唯一 Environment ID，因此失败会保留原选择。使用成功后，`HevSkillRegistry` 只展示 current Environment 中标为 `auto` 且存在原生 winner 的 Skill；无法在原生 Registry 中找到的 key 保持不可见，不导致 `use` 失败。

### 7.4 Plugin use 契约

```text
/hev env use <env-id-or-name>
    ↓
hev-runtime 入口按 JSON v2 解析 data.environment
    ↓
environmentIdBySession.set(agent.session, environment.id)
    ↓
HevSkillRegistry 从 options.scope 精确匹配 ctx.agents.list() 中的 live Agent
    ↓
current(agent.session, options.signal) 重新读取最新 Environment
    ↓
override snapshot/get 只保留 auto；父类 list 动态调用 override snapshot
```

`hev-runtime` 入口只在 CLI 成功返回且 [JSON v2](../contracts/cli/v2/) 校验通过后保存 `environment.id`；名称输入由 CLI 返回的规范 ID 取代，失败时保留该 Session 原有 ID。`HevSkillRegistry.snapshot()` 与 `get()` 每次从 `options.scope` 精确定位 live Agent，再通过异步 `current(agent.session, options.signal)` 读取最新 Environment；父类 `list()` 动态调用 override 后的 `snapshot()`。找不到精确 Agent 时保留原生 view；找到精确 Agent 但该 Session 未显式 `use` 时向 Core 查询默认 Environment；其余情况读取该 Session 自己保存的 ID。每条精确 Agent 路径都只展示 `auto` 且被列入的原生 winner。

### 7.5 兼容性规则

- 新增可选字段不升级 `schemaVersion`，Plugin 忽略未识别的可选字段。
- 删除字段、改变字段类型或改变现有语义时，必须升级 `schemaVersion`。
- Plugin 遇到不支持的 `schemaVersion` 时必须明确报错，不得猜测或降级解析。
