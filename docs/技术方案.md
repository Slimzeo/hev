完整的模型链应该是：

```
  CLI 输入模型
      ↓
  Application / Service 输入模型
      ↓
  Domain Model
      ↙                     ↘
  Repository 持久化模型      Runtime 输入/输出模型
      ↘                     ↙
  Application / Service 结果模型
      ↓
  CLI 输出模型
```

用业务 PSM 类比就是：

```
  IDL Req
  → Service Params
  → BO / Entity
  ↔ DO / PO、下游 RPC Req/Resp
  → Service Result
  → IDL Resp
```

注意：Service 和 Repository 是代码层；Input、Result、Record 等才是这些层持有或传递的模型。

**一、完整的模型分类**

| 模型层                       | CLI 项目命名        | 业务 PSM 类比   | 职责                           |
| ---------------------------- | ------------------- | --------------- | ------------------------------ |
| 外部输入                     | XxxArgs             | IDL Request     | 原样接收用户参数               |
| 应用输入                     | XxxInput            | Service Params  | 去掉 CLI 细节后的标准化输入    |
| 领域模型**(domain)**         | Environment         | BO / Entity     | 表示稳定业务对象               |
| 持久化模型<br />(repository) | Environment JSON   | DO / PO         | `JsonEnvironmentStore` 的内部格式 |
| Runtime 输入                 | []EnvironmentId      | Caller Request  | 本次要激活的 Environment，顺序即组合顺序 |
| Runtime 输出                 | ResolvedEnvironmentSnapshot | Caller Response | 解析后的环境与 Skill 策略视图 |
| 应用结果                     | XxxResult           | Service Result  | 表示一次业务用例的完整结果     |
| CLI 输出                     | XxxOutput / XxxView | IDL Response    | 面向用户展示的数据             |

后缀语义可以这样记：

- Args      外部 CLI 参数
- Input     Service 接收的应用输入
- Entity    业务中的稳定对象
- Spec      一个 Environment 内声明的 Skill 配置
- Snapshot  一次读取最新 Environment 后解析出的不可变视图
- Record    存储格式
- Result    Service 的执行结果
- Output    CLI 最终展示结构

### 3.1 Skill关键 domain model

1. `SkillKey`
   HEV Core 对一个逻辑 Skill 的稳定标识，不等同于 DSH、OpenCode 等宿主的原生对象。MVP 默认使用相同名称映射，但 Core 不导入任何宿主 Skill 类型。

   ```go
   type SkillKey string
   ```

2. `EnvironmentSkillSpec`
   抽象一个 Environment 如何使用某个 Skill。
   HEV 只保存逻辑 key，不复制 Skill 正文、物理路径或 Provider 私有 locator。

   ```go
   var skill_key SkillKey
   var policy EnvironmentSkillPolicy
   ```

3. `EnvironmentSkillPolicy`
   抽象 Skill 在一个具体 Environment 中的调用策略。
   这是 Environment 与 Skill 的关系属性，不是 Skill 自身的全局属性。

   ```go
   // auto | always | every-n-turns | off
   var kind string
   // 仅 kind == every-n-turns 时存在，并且必须大于 0
   var every_n_turns *uint64
   ```

   MVP 隔离链路先实现 `auto` 与 `off`。`always` 和 `every-n-turns` 先保留为扩展需求；实现时由 `hev-runtime` 的 root-Agent `SkillActivationDriver` 负责 turn 计数、串行调度与 teardown，不能由 Candidate restriction 冒充自动执行。

4. 不再保留 `SkillSharedCache`、`SkillManagement`、`SkillData`、`SkillIdentity` 和 `SkillEnvPath`
   `SkillSharedCache` 实际混合了 Registry cache 与 Skill 数据源两个职责；`SkillManagement` 与宿主已有 Registry 重复；`SkillData` 和物理地址已经由宿主 Skill Provider 管理。
   MVP 中 DSH Adapter 默认把 `skill_key` 等值映射到 `SkillCandidate.name`。等 Provider 真正提供稳定的 creator、version 和 content digest，并且产品要求锁定不可变制品时，再新增 `SkillArtifactRef` 与 `SkillArtifactStore`，不提前制造一套无法验证的身份。

### 3.2 Environment关键domain model



1. `EnvironmentId`
   Environment 的稳定唯一标识。Go Core 使用自有类型，避免与普通字符串混用。

   ```go
   type EnvironmentId string
   ```

2. `Environment`
   HEV 的核心领域实体，只描述环境本身及其 Skill 配置，不保存当前是否激活，也不保存宿主路径。

   ```go
   var id EnvironmentId
   var name string
   var revision uint64
   var skills []EnvironmentSkillSpec
   ```

   `revision` 仅作为未来 Environment 版本管理的预留字段。MVP 不提供历史版本查询、指定 revision 激活或回退能力，所有激活、恢复和 Skill 过滤逻辑都只按 `EnvironmentId` 读取 Store 中的最新 Environment，不用 revision 决定读取哪一版。

3. `ResolvedEnvironmentSnapshot`
   本次按 Environment ID 读取最新值并完成校验后的临时结果。CLI 与不同宿主 Adapter 只交换这个可序列化模型，Session 不持久化它。

   ```go
   var environments []Environment
   ```

   `environments` 表示同一时刻组合激活的多个 Environment，不是同一 Environment 的 revision 历史。每个元素里的 `revision` 仅用于展示当前读取结果；Session 只记录 Environment ID，下一次读取时重新解析最新值。MVP 组合多个 Environment 时若出现同名 Skill，直接返回冲突错误；确定覆盖或 alias 规则后再放宽。

### 3.3 Store与Runtime model

1. `EnvironmentStore`
   Environment 数据集的 CRUD owner。原 `EnvironmentRegistry` 改为这个名称，因为当前没有动态注册、优先级、effect 生命周期和 disposer，不符合 Registry 的职责。Store 面向 Core 返回 `Environment`，JSON 字段映射留在 `JsonEnvironmentStore` 内部；MVP 不为字段完全相同的数据额外公开 `EnvironmentRecord`。

   ```go
   Get(id EnvironmentId) (Environment, error)
   List() ([]Environment, error)
   Create(environment Environment) error
   Update(environment Environment) error
   Delete(id EnvironmentId) error
   ```

   MVP 每个 `EnvironmentId` 只保存一份当前记录，`Get` 只返回最新值。`JsonEnvironmentStore` 在创建时写入初始 revision、更新时自行递增；调用方不按 revision 查询或选择。历史版本存储、compare-and-set 和 rollback 都是后续版本管理能力，不在当前主流程中。文件锁、原子替换和 JSON schema 校验也由 `JsonEnvironmentStore` 负责。

2. `EnvironmentController`
   `hev-runtime` Plugin 导出的 Service，负责从 Session Event 恢复当前 Environment ID、读取最新 Environment 和接受环境切换。它通过 `environment/changed` 发布已经提交的变化，但不操作 `SkillRegistry` cache，也不发布 `skills/change`。
   它不替代 DSH 的 `AgentRegistry`、`SessionStore` 或 `SkillRegistry`。类名使用 `Controller`，因为 MVP 的公开职责是读取和改变 Environment 状态；等它真正拥有自动执行、取消和 teardown 生命周期时，再引入私有 Runtime/Driver。

   ```typescript
   interface EnvironmentSessionSource {
     readonly header: SessionHeader
     readonly events: readonly SessionEvent[]
   }
   
   export default class EnvironmentController extends Service {
     current(source: EnvironmentSessionSource): Promise<ResolvedEnvironmentSnapshot>
     activate(agent: Agent, environmentIds: readonly EnvironmentId[]): Promise<ResolvedEnvironmentSnapshot>
   }
   ```

   `EnvironmentSessionSource` 是 Adapter 内部最小只读输入 `{ header, events }`；live `Session` 直接满足，冷读 `SessionInspection` 将 `meta` 映射为 `header` 后满足。`current()` 从最后一个 `environment/selected` Event 取得 Environment ID，再通过 `EnvironmentStore.Get()` 读取最新值。

3. `EnvironmentCache` **（低优先级预留，MVP 不接入）**
   未来只在重复解析 Session Event 与 Environment Store 已被证明存在性能问题时，作为 `EnvironmentController` 的私有派生缓存；它不是公共 Domain Model，也不是持久真源。
   当前先保留结构草案，不在 `EnvironmentController` 中实例化。启用前必须同时处理 Environment Store 更新造成的失效，不能只依赖 `observedSeq`，否则会违反“始终读取最新 Environment”的语义。

   ```typescript
   interface EnvironmentCache {
     observedSeq: number
     snapshot?: ResolvedEnvironmentSnapshot
     skillPolicies: ReadonlyMap<string, EnvironmentSkillPolicy>
   }
   ```

4. `SkillActivationDriverState` **（低优先级预留，MVP 不接入）**
   未来启用 `always` 与 `every-n-turns` 后，由 `hev-runtime` 内部的 per-Agent driver 持有；当前只保留结构草案，不创建状态，也不进入 HEV Core 或 JSON。

   ```typescript
   interface SkillActivationDriverState {
     readonly agent: Agent
     completedRootTurns: number
     run?: Promise<void>
     stopping: boolean
   }
   ```

   后续实现时，driver 只统计已完成的 root turn，在下一次 accepted pre-step 注入 Skill 内容；`always` 每个 root turn 注入，`every-n-turns` 每 N 个完成的 root turn 注入。去重键、日志事件和 subagent 继承规则届时结合实际 Consumer 再确定，不属于 MVP 契约。

### 3.4 DSH Adapter复用与扩展的model

1. `SkillInvocationPolicy`
   直接复用 `@deepseek-ai/dsh-skill` 的调用入口策略。它只表示模型和用户两个入口是否允许调用，不表示 HEV 的自动触发频率。

   ```typescript
   interface SkillInvocationPolicy {
     readonly modelInvocable: boolean
     readonly userInvocable: boolean
   }
   ```

   复用原因：`dsh-tool-skill` 已经在 catalog、`skill` Tool 和用户 `/name` 入口执行这套策略。HEV 不复制这两个布尔字段；Environment 中的 `off` 由 restriction 强制隐藏，`auto` 保留原 Skill 自带的 invocation 值。

2. `SkillSummary`、`SkillResourceBase` 与 `SkillCandidate`
   直接复用 `@deepseek-ai/dsh-skill` 的 Skill 摘要、资源基址与候选模型。Provider 用 Candidate 做轻量发现，Registry 用 `rank`、Provider 注册顺序和本地顺序完成同名决胜；对外列表只暴露去掉 `rank` 和 `locator` 的 Summary。

   ```typescript
   type SkillSource =
     | 'project-dsh'
     | 'project-agents'
     | 'runtime'
     | 'user-dsh'
     | 'user-agents'
     | 'custom'
     | 'bundled'
     | (string & {})
   
   type SkillResourceBase =
     | { readonly kind: 'directory'; readonly path: string }
     | { readonly kind: 'url'; readonly url: string }
     | { readonly kind: 'opaque'; readonly description: string }
   
   interface SkillSummary {
     readonly name: string
     readonly description: string
     readonly whenToUse?: string
     readonly invocation: SkillInvocationPolicy
     readonly source: SkillSource
     readonly provider: string
     readonly resourceBase?: SkillResourceBase
   }
   
   interface SkillCandidate extends SkillSummary {
     readonly rank: number
     readonly locator: unknown
     readonly path?: string
     readonly metadata?: Readonly<Record<string, unknown>>
   }
   ```

   复用原因：HEV 只决定当前 Session 是否允许这个 Candidate，不能取代 Provider 的发现、排序和 locator 解释。`locator` 只留在 DSH Adapter 内，不写入 HEV Core 或 JSON。

3. `SkillDefinition`
   直接复用 `@deepseek-ai/dsh-skill` 的完整 Skill 模型，由获胜 Candidate 的原 Provider 延迟加载。

   ```typescript
   interface SkillDefinition extends SkillSummary {
     readonly content: string
     readonly path?: string
     readonly metadata?: Readonly<Record<string, unknown>>
   }
   ```

   复用原因：Skill 正文可能来自本地文件、runtime registration、bundled package 或远端 Provider。HEV 不复制正文，就不会出现两份 Skill 数据和两套失效规则。

4. `SkillProvider` 与 `SkillRegistry`
   继续复用 DSH 的 Provider/Registry 能力，不新建第二套 `SkillManagement`。`hev-skill` 只向 Registry 注册通用 Candidate restriction。以下列出 HEV 会使用的现有 public surface；`registerRestriction()` 单独放在第 8 项，因为它是拟议扩展。

   ```typescript
   interface SkillLookupOptions {
     readonly cwd?: string
     readonly signal?: AbortSignal
   }
   
   interface SkillProviderObservation {
     readonly candidates: readonly SkillCandidate[]
     readonly complete: boolean
   }
   
   interface SkillProvider {
     readonly name: string
     readonly list: (options: SkillLookupOptions) => Promise<readonly SkillCandidate[] | SkillProviderObservation>
     readonly get: (candidate: SkillCandidate, options: SkillLookupOptions) => Promise<SkillDefinition | undefined>
   }
   
   interface SkillProviderControl {
     readonly signal: AbortSignal
     readonly invalidate: () => void
   }
   
   class SkillRegistry extends Service {
     registerProvider(create: (control: SkillProviderControl) => SkillProvider): () => void
     list(options?: SkillViewOptions): Promise<SkillSummary[]>
     snapshot(options?: SkillViewOptions): Promise<SkillCatalogSnapshot>
     get(name: string, options?: SkillViewOptions): Promise<SkillDefinition | undefined>
   }
   
   interface SkillCatalogSnapshot {
     readonly skills: SkillSummary[]
     readonly complete: boolean
   }
   ```

   DSH 必须先按原有 rank、Provider 顺序和 scope shadowing 规则得到最终 winner，再对 winner 执行 restriction；被拒绝的 winner 不回退到较低优先级同名 Candidate。`list()`、`snapshot()`、`get()` 共用同一个受限 winner 结果。只过滤 `dsh-tool-skill` 或 `skill-filesystem` 都不能形成隔离。

5. `Session`
   `hev-runtime` 和 `hev-skill` 的 live path 直接使用 DSH 的精确 Session 对象。以下只是 HEV 使用到的字段，不是 Session 的完整定义。

   ```typescript
   class Session {
     readonly id: SessionId
     readonly header: SessionHeader
     readonly events: readonly SessionEvent[]
   }
   ```

   复用原因：Session Event 是 DSH live path 的持久真源，只传 `SessionId` 会迫使下层再次查全局 Store。标准冷读拿到的是 `SessionInspection { meta, events }`，不是 live `Session`；fold 逻辑应接收两者都能提供的最小 `{ header, events }` 只读结构，不能伪造 Agent 或 Session。

6. `Agent`
   `EnvironmentController.activate()` 复用 DSH 的 live Agent handle。以下只列 HEV 使用到的字段，不是 Agent 的完整定义。

   ```typescript
   interface Agent {
     readonly id: SessionId
     readonly session: Session
     readonly status: 'idle' | 'running'
     readonly ctx: Context
   }
   ```

   复用原因：环境切换发生在某个精确 live Agent 生命周期中，需要使用其 Session 作为持久真源，并由 agent-scoped effect 管理监听和清理。HEV 不创建第二个 Agent model，Core 也不接收 Agent。

7. `SkillViewOptions`
   `scope` 继续决定 DSH Provider contribution chain；新增的 `session` 只表示本次 Skill view 所属的业务 Session。当前 DSH 只有 `scope`，所以下面的 `session` 是拟议扩展，不是现有字段，也不属于 HEV Core。

   ```typescript
   interface SkillViewOptions extends SkillLookupOptions {
     readonly scope?: ScopeKey
     readonly session?: Session
   }
   ```

8. `SkillRestriction`
   当前 DSH 尚无该类型和注册方法；这是拟议增加到 `dsh-skill` 的通用扩展点，不包含 HEV、Environment 等产品词汇。`hev-skill` 通过它读取显式 `options.session` 并执行 Environment policy。

   ```typescript
   type SkillRestriction = (
     candidate: SkillCandidate,
     options: SkillViewOptions,
   ) => boolean | Promise<boolean>
   
   interface SkillRestrictionControl {
     // 只通知 Consumer 重新读取；provider-neutral winner cache 无需失效
     notifyChange(): void
   }
   
   class SkillRegistry extends Service {
     registerRestriction(
       create: (control: SkillRestrictionControl) => SkillRestriction,
     ): () => void
   }
   ```

   restriction 只负责 Session 级可见性：未被当前 Environment 选择的 Skill 和 `off` Skill 不可见；`auto` 保留宿主原生按需调用。`always`、`every-n-turns` 不由 restriction 执行。

   `SkillRegistry` 注册 restriction 时返回 disposer。现有 provider-neutral winner cache 继续只缓存原生 winner；restriction 在 cache 读取之后按本次 `options.session` 动态执行，其结果不写回原 `collectCache`，因此不会让相同 cwd/scope 的两个 Session 互相污染。Environment 切换提交后 `hev-runtime` 只发布 `environment/changed`；`hev-skill` 收到后调用 registration-scoped `control.notifyChange()`，由 Registry 发布 `skills/change`，不直接操作 Registry 私有 cache。由于 restriction 每次动态执行，Environment 变化不需要清除 provider-neutral winner cache。若 DSH 暂时不能提供该 seam，兼容 Registry fork 只能作为 PoC 兜底，不能进入 HEV Core。

9. `hev-runtime` 与 `hev-skill` 的 Plugin 结构
   `hev-runtime` 是 Service package，默认导出 `EnvironmentController`，并按 DSH 的单数 service key 规则注册为 `ctx.environment`；`hev-skill` 不提供第二个 `ctx.skills`，而是作为 function plugin 注册 restriction。

   ```typescript
   // hev-runtime
   declare module '@deepseek-ai/cordis' {
     interface Context {
       environment: EnvironmentController
     }
   }
   
   export default class EnvironmentController extends Service {
     constructor(ctx: Context) {
       super(ctx, 'environment')
     }
   }
   
   // hev-skill
   export const name = 'hev-skill'
   export const inject = ['skills', 'environment']
   
   export function apply(ctx: Context): void {
     ctx.skills.registerRestriction(control => async (candidate, options) => {
       if (options.session === undefined) return false
       const snapshot = await ctx.environment.current(options.session)
       return allowsSkill(snapshot, candidate.name)
     })
   }
   ```

   这与 DSH 的 package 规则一致：Service package 默认导出 Service class；只贡献行为的 Plugin 使用 `name / inject / apply` 命名导出。若代码进入 DSH monorepo，包名使用 `@deepseek-ai/dsh-hev-runtime` 与 `@deepseek-ai/dsh-hev-skill`；若留在独立 HEV 仓库，则使用 HEV 自己的 package scope。

### 3.5 复用边界与跨宿主迁移

复用 DSH model 的确会让 **DSH Adapter** 依赖 DSH，但这是 Adapter 的职责，不等于 HEV Core 与 DSH 耦合。依赖方向固定为：

```text
HEV Core（SkillKey / Environment / Snapshot / Policy）
    ↑
    ├── DSH Adapter（SkillCandidate / SkillDefinition / Session）
    └── OpenCode Adapter（OpenCode native skill / session model）
```

HEV Core 不导入 Cordis、DSH `Session`、`Agent`、`ScopeKey`、`SkillCandidate` 或 `locator`。迁移到 OpenCode 时保留 Environment JSON、CLI 用例和 policy 解析，只新增 OpenCode Adapter，将 `EnvironmentSkillSpec.skill_key` 映射到 OpenCode 的原生 Skill name，并用 OpenCode 的 Session 生命周期保存当前激活的 Environment ID。MVP 可约定逻辑 key 与各宿主原生 name 相同；若名称不同，映射只进入对应 Adapter 配置。如果 OpenCode 没有 Registry 过滤扩展点，Adapter 需要使用它支持的受控 Skill root 或配置投影实现隔离；不把该差异反向塞进 Core。

## 四、接口设计

Args（即对应互联网开发HTTP层）设计：
模仿：conda，使用 Go 的 Cobra 创建 CLI 后，会自动提供 --help 和 -h。

而在cli层的调用接口如下
```bash
  hev env create <env-name> [env-name...]
  hev env remove <env-name> [env-name...]     # alias: rm
  hev env list
  hev env rename <old-name> <new-name>
  hev env activate <env-name>
  hev env deactivate
  hev env get <env-name> # 返回内容同hev env activate <env-name>，只是语义不同
  hev skill list -a/-e <-e的时候指定env>
  hev skill add <skill_name> <env_list>
```

在ts plugin中最终调用的示例如下，
```bash
# env
/hev env -c/create <env-name>
/hev env -rm/remove <env-name>
/hev env list
/hev env -rn/rename <old-env-name> <new-env-name>
/hev env -a/activate <env-name>
# 取消当前环境组，回到 base
/hev env -d/deactivate
```

## 五、技术栈选择
做一个core + adapter两层架构
core底层逻辑维持不变，adapter用于兼容dsh, claude code, codex

core：从熟悉度角度暂时选型go，使用cobra封装一个轻量CLI

adapter：对于第一步适配的dsh来说，写一个typescript的plugin

## 六、存储层设计
MVP 暂定只使用 JSON 持久化 HEV 自有的 `Environment`。Skill 的发现、正文和物理位置继续由各宿主的原生 Skill Provider 管理；HEV 不保存第二份 `skills.json`。

### 6.1 Environment Store

`$HOME/.hev/environments.json`

```json
{
  "schemaVersion": 1,
  "environments": [
    {
      "id": "env_01",
      "name": "base",
      "revision": 1,
      "skills": [
        {
          "skillKey": "common-env-init",
          "policy": {
            "kind": "auto"
          }
        }
      ]
    }
  ]
}
```

`policy.kind` 取值为 `auto`、`always`、`every-n-turns` 或 `off`；`always` 和 `every-n-turns` 在 MVP 中先作为未启用的扩展值，不能配置。后续启用 `every-n-turns` 时额外保存大于 `0` 的 `everyNTurns`。`JsonEnvironmentStore` 是 `EnvironmentStore` 的第一版实现。

`base` 是启动时必须存在的普通 Environment，由初始化命令创建，不在 Plugin 内硬编码内容。缺失时 `activate` 和 `deactivate` 都明确返回 `BASE_ENV_NOT_FOUND`；它的 revision 与其他 Environment 一样通过 `EnvironmentStore` 更新。

### 6.2 DSH Session选择

DSH Adapter 不把当前激活状态写入全局 JSON。`hev-runtime` 激活时先按 Environment ID 读取 Store 中的最新值并完成校验，提交时只把 Environment ID 列表写入当前 Session Event。恢复和 Skill 过滤时再次按这些 ID 读取最新 Environment，因此 Environment 更新后，已有 Session 也绝对跟随最新结果。

```json
{
  "type": "environment/selected",
  "data": {
    "environmentIds": ["env_01"]
  }
}
```

Session Event 不保存 Environment 的 `revision`、Skill 配置或 `ResolvedEnvironmentSnapshot`。`revision` 目前只是 Environment 当前记录上的预留字段；Session 不按 revision 查询、锁定或回退版本。当前 DSH 不支持仓外 Plugin 注册恢复所必需的 Session Event，因此 `environment/selected` 是需要进入 DSH 主仓、扩展 `SessionEventMap` 并重新生成 known-event catalog 的拟议改动；在该能力落地前，仓外 PoC 必须使用独立 sidecar，不能把该事件标成可忽略后假装完成恢复。

## 七、CLI 与 Plugin 契约

DSH Plugin 通过子进程调用 `hev` CLI，复用 Go Core 的 Environment use case。CLI 负责 Environment 持久化并按 ID 解析最新配置，Plugin 负责用 DSH Skill Registry 校验 Skill，并把 Environment ID 列表写入 Harness Session；CLI 不保存“当前激活环境”。未来接入 OpenCode 时复用同一 CLI 与 JSON，只替换宿主 Adapter。

### 7.1 调用规则

- Plugin 调用 CLI 时固定传入 `--output json`。
- `stdout` 只输出一个 JSON 对象，`stderr` 只输出日志和诊断信息。
- 成功时退出码为 `0`，失败时为非 `0`；失败时 `stdout` 仍返回结构化错误。
- Plugin 必须先校验 `schemaVersion` 和 JSON 结构，再使用返回数据。

### 7.2 公共返回结构

成功：

```json
{
  "schemaVersion": 1,
  "code": 200,
  "message": "success",
  "prompt": "",
  "data": {}
}
```

失败：

```json
{
  "schemaVersion": 1,
  "code": 404,
  "message": "environment not found: coding",
  "prompt": "run hev env list to inspect available environments",
  "data": {
    "errorCode": "ENV_NOT_FOUND"
  }
}
```

`code` 是数字状态码；`data.errorCode` 是给 Plugin 判断的稳定错误码；`message` 用于向用户展示，`prompt` 用于提供下一步提示。Core/CLI 错误码包括：`INVALID_ARGUMENT`、`ENV_NOT_FOUND`、`BASE_ENV_NOT_FOUND`、`ENV_ALREADY_EXISTS`、`SKILL_ALREADY_BOUND` 和 `INTERNAL_ERROR`。`SKILL_NOT_FOUND` 属于 Adapter 校验错误，不由不访问宿主 Registry 的 Core/CLI 产生。

### 7.3 CLI 命令契约

#### 创建 Environment

```bash
hev env create <env-name> --output json
```

```json
{
  "schemaVersion": 1,
  "code": 200,
  "message": "environment created",
  "prompt": "",
  "data": {
    "environment": {
      "id": "env_01",
      "name": "coding",
      "revision": 1,
      "skills": []
    }
  }
}
```

#### 注册 Skill 并加入 Environment

```bash
hev skill add <skill-key> --env <env-name> [--env <env-name>...] [--policy <auto|off>] --output json
```

```json
{
  "schemaVersion": 1,
  "code": 200,
  "message": "skill added to environment",
  "prompt": "",
  "data": {
    "environmentSkill": {
      "skillKey": "code-review",
      "policy": {
        "kind": "auto"
      }
    },
    "environments": [
      {
        "id": "env_01",
        "name": "coding",
        "revision": 2
      }
    ]
  }
}
```

MVP 传入的是 HEV `skill-key`，CLI 只在指定 Environment 中写入 `EnvironmentSkillSpec`，不复制 Skill 正文或物理路径。MVP 只接受 `--policy auto|off`；`always` 与 `every-n-turns` 等 `SkillActivationDriver` 落地后启用。DSH Adapter 默认将 `skill-key` 等值映射为 `SkillCandidate.name`，并在收到 `ResolvedEnvironmentSnapshot` 后向 Registry 校验；任何 Skill 不可解析时，Adapter 拒绝提交。

#### 激活 Environment 组

```bash
hev env activate <env-id-or-name> [env-id-or-name...] --output json
```

```json
{
  "schemaVersion": 1,
  "code": 200,
  "message": "environment snapshot resolved",
  "prompt": "",
  "data": {
    "snapshot": {
      "environments": [
        {
          "id": "env_01",
          "name": "coding",
          "revision": 2,
          "skills": [
            {
              "skillKey": "code-review",
              "policy": {
                "kind": "auto"
              }
            }
          ]
        }
      ]
    }
  }
}
```

CLI 按入参顺序读取最新 Environment，并返回本次临时的 `ResolvedEnvironmentSnapshot`。其中的 `revision` 只展示本次读到的当前值，不参与选择。Core 校验 Environment 与 policy；Adapter 再使用宿主原生 Registry 校验 Skill name。任一 Environment 不可用时 CLI 整体失败；任一 Skill 不可解析时 Adapter 拒绝提交，不产生新的 Session Event。

#### 取消激活

```bash
hev env deactivate --output json
```

```json
{
  "schemaVersion": 1,
  "code": 200,
  "message": "base environment snapshot resolved",
  "prompt": "",
  "data": {
    "snapshot": {
      "environments": [
        {
          "id": "env_base",
          "name": "base",
          "revision": 1,
          "skills": [
            {
              "skillKey": "common-env-init",
              "policy": {
                "kind": "auto"
              }
            }
          ]
        }
      ]
    }
  }
}
```

`deactivate` 的固定语义是取消当前 Environment 组并返回 `base` 的完整 snapshot；即使当前已经是 `base`，也返回成功。

### 7.4 Plugin 激活契约

```text
/hev env activate <env-name> [env-name...]
    ↓
hev-runtime 调用 CLI 解析 ResolvedEnvironmentSnapshot
    ↓
使用 DSH SkillRegistry 校验 snapshot 中的 Skill name
    ↓
向当前 Session append 只携带 environmentIds 的 environment/selected
    ↓
hev-runtime 发布 environment/changed；hev-skill 通过 restriction control 请求 Registry 发布 skills/change
```

Session Event 只保存 6.2 所示的 `environmentIds`。`/hev env deactivate` 使用相同流程提交 `base` 的 ID。Session 恢复时，`hev-runtime` fold 最后一个 `environment/selected` Event，按 ID 从 Store 读取最新 Environment，并在首次受限 Skill view 返回前校验其中的 Skill。切换操作必须串行化；最新 Environment 未完整解析和校验前继续保留旧状态，只有 Session Event append 成功后才发布变更，不直接替换或重新装载 Skill Provider。

### 7.5 兼容性规则

- 新增可选字段不升级 `schemaVersion`，Plugin 忽略未识别的可选字段。
- 删除字段、改变字段类型或改变现有语义时，必须升级 `schemaVersion`。
- Plugin 遇到不支持的 `schemaVersion` 时必须明确报错，不得猜测或降级解析。
