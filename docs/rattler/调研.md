
**二、核心 Domain Model**

你的产品边界下，真正稳定的领域对象只有两个。

```
// Environment 表示一个由本应用管理的隔离环境。
type Environment struct {
    // 用户操作环境时使用的名称。
    Name string
    // 环境在磁盘上的根目录。
    Prefix string
}
```

职责：

- 表示“一个环境是什么”；
- 被 create 产生；
- 被 env list 返回；
- 被 activate、switch 定位；
- 与包下载、shell 状态、CLI 参数无关。

```
// InstalledPackage 表示从一个环境中观察到的已安装包。
type InstalledPackage struct {
    // 包名。
    Name string
    // 已安装版本。
    Version string
}
```

职责：

- 表示 list 查询到的包；
- 是当前环境实际状态的只读视图；
- 不表示用户期望安装什么；
- 不负责下载、解析或安装。

**三、create 的完整模型链**

**CLI 输入模型**

```
type CreateEnvironmentArgs struct {
    // 用户在命令行输入的环境名。
    Name string
}
```

对应：

```
rattler env create demo
```

**Service 输入模型**

```
type CreateEnvironmentInput struct {
    // 校验、标准化之后的环境名。
    Name string
}
```

它与 Args 目前字段相同，但语义不同：

- Args 属于 Cobra；
- Input 属于应用用例；
- 以后换成 HTTP/RPC 时，Service 不需要依赖 Cobra。

如果项目足够小，也可以暂时省略这个转换，直接使用 string。但从完整分层看，它处于这一位置。

**Runtime 输入模型**

```
type CreatePrefixInput struct {
    // 要创建环境的最终磁盘位置。
    Prefix string
}
```

职责：

- 只告诉运行时“在哪里创建隔离环境”；
- 不包含环境名，因为 Python/操作系统不关心业务名称；
- 不包含包列表，因为用户自己执行 pip install。

**Domain Model**

物理环境创建成功后，Service 形成：

```
Environment{
    Name:   "demo",
    Prefix: "/managed/envs/demo",
}
```

**Repository 持久化模型**

```
type EnvironmentRecord struct {
    // 写入 registry 的环境名。
    Name string `json:"name"`
    // 写入 registry 的环境路径。
    Prefix string `json:"prefix"`
}

type RegistryFile struct {
    // 持久化格式版本，用于后续兼容升级。
    Version uint32 `json:"version"`
    // 所有已登记环境。
    Environments []EnvironmentRecord `json:"environments"`
}
```

它们属于 Repository 私有模型：

```
  Environment       业务对象
        ↕
  EnvironmentRecord 磁盘记录
```

**Service 结果模型**

```
type CreateEnvironmentResult struct {
    // 已创建并成功登记的环境。
    Environment Environment
}
```

它表示整个用例已经成功： 物理环境创建成功 + registry 登记成功

**CLI 输出模型**

```
type CreateEnvironmentOutput struct {
    // 创建成功的环境名。
    Name string
    // 创建成功的环境路径。
    Prefix string
}
```

完整链路只有模型，不用函数占位：

```
  CreateEnvironmentArgs
  → CreateEnvironmentInput
  → CreatePrefixInput
  → Environment
  → EnvironmentRecord / RegistryFile
  → CreateEnvironmentResult
  → CreateEnvironmentOutput
```

**四、env list 的完整模型链**

env list 没有实际输入参数，不需要为了形式硬造一个空 struct。

```
  RegistryFile
  → []EnvironmentRecord
  → []Environment
  → ListEnvironmentsResult
  → ListEnvironmentsOutput
```

**Service 结果：**

```
type ListEnvironmentsResult struct {
    // 所有由本应用管理的环境。
    Environments []Environment
    // 当前 shell 正在使用的环境路径，仅用于计算展示状态。
    ActivePrefix *string
}
```

**CLI 输出：**

```
type EnvironmentView struct {
    Name string
    Prefix string
    // 只表示当前这次 CLI 调用所在 shell 是否激活了该环境。
    Active bool
}

type ListEnvironmentsOutput struct {
    Environments []EnvironmentView
}
```

为什么 active 放在 EnvironmentView，不放 Environment？

因为：

- Environment 是全局稳定对象
- active 是当前 shell 下的临时展示状态

终端 A 可能激活 demo，终端 B 没有激活。环境自身不能有全局 `Active bool`。

**五、list 包列表的完整模型链**

**CLI 输入：**

```
type ListPackagesArgs struct {
    // 用户输入的环境名。
    Environment string
}
```

**Service 输入：**

```
type ListPackagesInput struct {
    // 标准化后的目标环境名。
    EnvironmentName string
}
```

Repository 中先读取环境：

```
  EnvironmentRecord
  → Environment
```

然后读取 pip 输出。如果通过：

```
python -m pip list --format=json
```

那么适配器内部可以有：

```
type PipPackageRecord struct {
    Name string `json:"name"`
    Version string `json:"version"`
}
```

再转换成 Domain：

```
  PipPackageRecord
  → InstalledPackage
```

**Service 结果：**

```
type ListPackagesResult struct {
    // 被查询的环境。
    Environment Environment
    // 该环境实际安装的包。
    Packages []InstalledPackage
}
```

**CLI 输出：**

```
type InstalledPackageView struct {
    Name string
    Version string
}

type ListPackagesOutput struct {
    EnvironmentName string
    Packages []InstalledPackageView
}
```

完整模型链：

```
  ListPackagesArgs
  → ListPackagesInput
  → EnvironmentRecord
  → Environment
  → PipPackageRecord
  → InstalledPackage
  → ListPackagesResult
  → ListPackagesOutput
```

**六、activate 的完整模型链**

**CLI 输入：**

```
type ActivateEnvironmentArgs struct {
    // 要激活的环境名。
    Environment string
    // 用户显式指定的 shell；未指定时自动检测。
    Shell *string
}
```

**Service 输入：**

```
type ActivateEnvironmentInput struct {
    EnvironmentName string
    Shell string
}
```

Repository 读取：

```
  EnvironmentRecord
  → Environment
```

Runtime 输入模型就是现有的 ActivationVariables，它应该留在 runtime，而不是 Domain：

```
type ActivationVariables struct {
    // 当前 shell 已激活的 prefix。
    CondaPrefix *string
    // 当前 PATH。
    Path []string
    // 当前环境变量。
    CurrentEnv map[string]string
}
```

再组合出激活请求：

```
type ActivationRequest struct {
    // 要激活的目标环境。
    Target Environment
    // 当前 shell 状态。
    CurrentShell ActivationVariables
    // 目标 shell 类型。
    Shell string
}
```

**Runtime 输出：**

```
type RenderedShellScript struct {
    // 需要由当前 shell 执行的脚本文本。
    Contents string
}
```

**Service 结果：**

```
type ShellTransitionResult struct {
    // 切换前的环境；此前没有环境时为空。
    From *Environment
    // 切换后的环境；退出环境时为空。
    To *Environment
    // 调用方需要执行的 shell 脚本。
    Script RenderedShellScript
}
```

CLI 最终必须原样输出 shell 脚本，所以不需要再包一层 ActivateResponse：

```
  ActivateEnvironmentArgs
  → ActivateEnvironmentInput
  → EnvironmentRecord
  → Environment
  → ActivationVariables
  → ActivationRequest
  → RenderedShellScript
  → ShellTransitionResult
  → stdout
```

**七、deactivate 的完整模型链**

**CLI 输入：**

```
type DeactivateEnvironmentArgs struct {
    Shell *string
}
```

**Service 输入：**

```
type DeactivateEnvironmentInput struct {
    Shell string
}
```

它不需要环境名，因为当前环境来自：

- CONDA_PREFIX
- CONDA_SHLVL
- CONDA_ENV_SHLVL_*

**Runtime 输入：**

```
type DeactivationRequest struct {
    // 当前 shell 状态及激活层级。
    CurrentShell ActivationVariables
    // 目标 shell 类型。
    Shell string
}
```

输出继续复用： `RenderedShellScript`

```
ShellTransitionResult{
    From:   &current,
    To:     previousOrNil,
    Script: script,
}
```

完整模型链：

```
  DeactivateEnvironmentArgs
  → DeactivateEnvironmentInput
  → ActivationVariables
  → DeactivationRequest
  → RenderedShellScript
  → ShellTransitionResult
  → stdout
```

**八、switch env 的完整模型链**

**CLI 输入：**

```
type SwitchEnvironmentArgs struct {
    TargetEnvironment string
    Shell *string
}
```

**Service 输入：**

```
type SwitchEnvironmentInput struct {
    TargetEnvironmentName string
    Shell string
}
```

中间模型可以全部复用：

```
  目标 EnvironmentRecord
  → 目标 Environment
  当前 ActivationVariables
  → ActivationRequest
  → RenderedShellScript
  → ShellTransitionResult
```

结果：

```
ShellTransitionResult{
    From:   &oldEnvironment,
    To:     &newEnvironment,
    Script: script,
}
```

所以 switch 需要自己的 Input，但不需要重新造一套 Domain Model 或 Runtime Model。

**最终目录应该体现模型属于哪一层**

```
src/
├── command/
│   ├── create.go          # CreateEnvironmentArgs / Output
│   ├── env_list.go        # ListEnvironmentsOutput
│   ├── list.go            # ListPackagesArgs / Output
│   ├── activate.go        # ActivateEnvironmentArgs
│   ├── deactivate.go      # DeactivateEnvironmentArgs
│   └── switch.go          # SwitchEnvironmentArgs
│
├── application/
│   └── environment.go     # XxxInput / XxxResult
│
├── model/
│   ├── environment.go     # Environment
│   └── installed_package.go
│
├── repository/
│   ├── environment_registry.go
│   │                      # RegistryFile / EnvironmentRecord
│   └── pip_metadata.go    # PipPackageRecord
│
└── runtime/
    └── activation.go      # ActivationVariables
                           # ActivationRequest
                           # DeactivationRequest
                           # RenderedShellScript
```

**最终要点是：**

- Args        外部用户说了什么
- Input       应用理解成了什么
- Domain      我们管理的对象是什么
- Record      这个对象怎么落盘
- Runtime DTO 操作系统组件需要什么、产出什么
- Result      这次业务操作得到了什么
- Output      最终给用户展示什么

“完整模型层次”不表示每一层必须机械复制相同字段。只有边界语义确实不同才拆 struct；没有输入的 env list 不必造空模型，直接复用 Environment 也不必再包一层同构 BO。
