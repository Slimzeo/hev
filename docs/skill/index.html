00 · Research argument

研究问题不是“Skill 有没有用”，而是 utility 在哪里产生、又在哪里失真。

精确问题：目标模型自己的成功与失败轨迹，经不同 extractor 压缩成 domain-level skill 后，再回灌到同一个 target 的 held-out 任务上，什么时候提高表现，什么时候造成 negative transfer？一份 skill 的 utility 究竟属于文本、extractor、target，还是三者与 domain 的交互？PDF p.2–5 · Figure 1 · Eq.1–5

Why

为什么写

既有 benchmark 多只测 consumption，绕过 raw experience 与 extraction，无法解释失败从哪一段进入。PDF p.1–3。

Problem

研究问题

能否把 experience、extractor、consumer 分开测，并识别“看似好 skill”与真实 utility 的差距？

Protocol

最小闭环

自生成轨迹 → 逐轨迹 pattern → 分层合并 → 单 skill 注入 → held-out delta。PDF p.3–5。

Metric

Δ / EE / TE

Δ 测单元干预；EE 跨 target 看 extractor；TE 跨 extractor 看 target。均只在同 domain 内解释。

Diagnosis

三段都变

experience 配比、skill 内容、target consumption ability 都会改变结果；格式与文本观感不足以代理 utility。

Intervention

Validated meta-skill

失败机制、可执行具体性、高风险黑名单在 9 个验证单元相对 original 平均 +1.55pp。PDF p.10–11, 22。

Boundary

证据边界

单 domain、单 skill、直接 prompt 注入；无大型 library selection/composition，主矩阵缺置信区间。

为什么可信

不是因为一个 Demo 看起来成功：Table 1 用 150-cell cross matrix 建立“平均有益但会伤害”；Figure 2–4 分段干预/对照 experience、text 与 consumer；Appendix C/E/F 给出格式检验、151-pair judge 协议与 alternative harness；Table 11 把诊断反馈为生成干预。可信度同时受限于三轮均值无置信区间、rubric 发现与评估同源风险、meta-skill 只验证 9 cells。PDF p.6–11, p.18–24
