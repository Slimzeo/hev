Architecture decision guide
Local manuscript · 2026-08-13
Spatiotemporal composability / 架构评审版

不要为了热更新，
引入一套新范式。

只有当系统必须在同一进程内频繁替换组件，还要同时保住运行态、精确撤回组件贡献，并随 provider 变化协调 dependent 生命周期时，时空组合性才值得进入候选集。

工程判断 它不是容器、DI 或 HMR 的高级替代品，而是一种更细粒度的运行时治理成本。先证明粒度错配真实存在，再承担这份成本。

Executive decision

先问四个问题。
缺一个，就先不迁。

论文把动态组合拆成两个正交问题：组件离开时能否撤回它对共享环境的修改；依赖出现、消失或换身份时，系统能否重新解析并协调生命周期。论文事实 p.4–6

01

必须细到进程内组件吗？

如果服务或进程级重启已满足可用性，容器的粗粒度边界更简单。

02

组件会长期反复变吗？

一次性启动装配不需要运行时生命周期 calculus。

03

效果能被中介与恢复吗？

隐藏写、不可逆 emission 和不受控 module side effect 会穿透保证。

04

依赖变化必须驱动生命周期吗？

若只需取一个对象，普通 DI 足够；关键是 provider 变化后的重解析。

工程判断 四项都是“是”，并且现有方案的重启代价、状态损失或手写 teardown 风险已经可观测，才进入 PoC。否则保持容器 + DI + 局部 HMR 的组合。

这项决策买到的，不是“插件化”三个字

目标是把一次动态变更约束成可推理的闭环：组件用普通操作安装资源与依赖，runtime 同步记录 inverse；依赖满足度变化触发生命周期；卸载按依赖顺序 drain，并只撤销目标 fiber 的贡献。论文进一步在明确前提下给出恢复精确性、provider/consumer 顺序、resolution coherence、progress 与 confluence。论文事实 p.28–53

这不是无条件事务。inverse 正确性、不同 fiber 的 independence、有限 iterator、无环 precedence，以及最终无失败和 provision totality，分别约束不同定理。论文事实 p.43–53

Research argument / adoption contract

通过四问 Gate 后，
还要看论文究竟证明了什么。

论文事实 精确研究问题是：进程内组件持续增删、替换时，能否只撤销离场组件自己的 context contribution，并在 provider 变化时自动协调 dependent 的重解析与生命周期？它把问题拆为 temporal / spatial composability；不是单纯 loader、cleanup 或 DI feature。p.4–8

GAP

既有方案为何不够

进程重启过粗；手写 dispose 难从安装逻辑导出完整恢复；初始化期 DI 不定义运行时 provider 变化和异步 drain。

M1

局部机制

revertible effect 同地返回 inverse；reactive coeffect 声明依赖并响应满足性变化；统一 context 约束共享访问。

M2

系统机制

component/fiber/registry 与四态 lifecycle、十条规则把撤出、异步、失败和依赖顺序变成 operational semantics。

M3

工程落点

Cordis API/字段、声明式 reconciliation 与 transactional HMR 对应形式对象和失败路径。

依据分三级，决策时不能互相替代

Goals & mechanics

设计目标：让“离场”与“换人”成为正常路径。

时空组合性不是一个 loader feature，而是 effect、dependency 与 lifecycle 三者共享同一运行时边界。

五个架构目标与保证边界

T

目标一：组件级恢复，而不是进程级重建

在 pairwise independence 等条件下，一个 fiber 的 accumulator 只撤销自己的贡献，保留交错执行的其他 fiber 效果。

Fit / no-fit matrix

适用的不是“复杂系统”，
而是特定的动态负载。

工程判断 用行为约束做 Gate，不用“平台化”“插件化”“Agent 化”做理由。

值得做 PoC 的条件

✓

进程内组件需要在不中断宿主的前提下反复增删

例如开放插件宿主、长寿命交互 runtime、会持续改变工具与策略的 harness。

验证：整进程重启是否丢失 cache、连接、session 或 in-flight task？
✓

provider 的出现、消失与换身份必须驱动 dependent 的进入和退出

依赖不是初始化时拿一次引用，而是运行中变化的拓扑。

验证：provider 变化后，现有 dependent 是否必须 drain / re-init？
✓

大部分 effect 可以经统一 context 或受控接口执行

资源 acquisition 可以配 inverse；外部 emission 可以延迟提交或业务补偿。

验证：列出每个 atomic effect、inverse 与 system boundary。
✓

团队愿意把 dependency declaration 当成架构契约

key、类型、版本、provider 唯一性、isolation realm 与访问路径必须可审计。

验证：依赖图能否静态导出、查环、做版本兼容检查？

明确不适用或暂缓

×

服务级 rollout 已满足需求

无珍贵进程态，副本冗余成本可接受，网络边界也符合领域边界。保留容器编排。

选择：container / process restart
p.5–6, p.73
×

变化只发生在启动或发布窗口

初始化装配 + DI 的复杂度更低，没必要引入持续 reconciliation。

选择：module wiring / DI
p.78
×

核心价值来自不可逆外部 emission

邮件、支付、消息已被外部参与者消费后，inverse 不能恢复原世界；只能 withholding 或 compensation。

先解决：outbox / saga / idempotency
p.67–68
×

不可信插件需要强隔离

Context Proxy 只能做 capability mediation，不能替代进程、sandbox 或容器边界。

先解决：sandbox / process isolation
p.69–70
×

依赖接口与版本仍靠字符串 key 猜测

论文明确指出 interface drift 与 key collision；coeffect satisfaction 不能证明语义兼容。

先解决：namespace / version / structural checks
p.72
Trade-off landscape

它与容器、DI、HMR、OSGi、FRP
不是同一层的竞品。

比较前先对齐粒度与目标。下表是能力边界，不是总排行榜。

Choose containers

边界就是进程，重建就是恢复

容器拥有更强隔离与成熟运维面。论文自身也把 OS / container 描述为 coarse-grained substitute；只有粒度错配造成真实代价时才下沉。

Choose DI

依赖拓扑稳定，只需要解耦构造

如果 provider 不会在运行中换身份，响应式 coeffect 的生命周期成本没有收益。

Choose HMR / DSU

目标是版本前进，不是完整离场

需要保留模块自身内存态时，forward migration 可能优于“撤回旧组件再从干净状态重放”。Cordis 的组件私有内存默认不会跨 reload 保留。p.76–77

Choose OSGi

动态服务模型已与生态匹配

它是 reactive service availability 的最接近先例。时空组合性增加的是结构化 effect recovery 与异步 teardown 语义，不是抹去生态成本。

Compose with FRP

组件级与值级变化同时存在

coeffect 可以承载 reactive value；FRP 负责值传播一致性，component lifecycle 负责资源与依赖离场。两者可叠加，不必二选一。p.79

Choose spatiotemporal

替换、撤回、重解析必须成为同一个原子叙事

真正独特的组合是：effect 与 dependency 通过同一 context 被归属到 fiber，provider 退出顺序与 inverse recovery 同属一个 lifecycle。

Migration gates

迁移不是改 loader，
而是逐步收紧系统边界。

工程判断 采用 strangler 路线：先选一个效果可枚举、依赖图小、回滚价值高的组件族。每个 Gate 都要能独立否决后续投入。

证明粒度错配

记录现有重启频率、状态重建时间、in-flight 中断、冗余副本与手写 teardown 缺陷。没有基线，就无法证明新 runtime 的收益。

Pass when问题可量化，且组件级恢复有明确 SLO / 成本目标。

Stop：现有容器或 HMR 已达标。

画出 effect boundary

逐项分类：纯计算、可逆 acquisition、可延迟 emission、可补偿 emission、不可恢复 emission。任何隐藏写都先暴露到受控接口。

Pass when试点组件的 atomic effect、inverse、owner、失败注入点可枚举。

Stop：核心价值依赖无法中介的不可逆 emission。

定义 dependency contract

建立 key namespace、typed interface、版本策略、provider 唯一性与 isolation realm；导出静态依赖图并检查环。

Pass when依赖声明可审计，cycle 已拆解，interface drift 有检测。

Stop：相同 key 可绑定语义不兼容对象。

先实现最小 runtime

只做 context mediation、inverse stack、fiber ownership、committed view 与 guarded withdrawal；不要先做全量 loader、HMR 或跨进程抽象。

Pass when单组件 LIFO recovery 与两组件 provider/consumer drain 可重复通过。

Stop：必须靠旁路写才能完成核心业务。

用对抗性交错验证保证

覆盖 reload 中 provider 消失、异步 setup 落地后 target 已变、inverse 失败、重复 retire、依赖暂缺、进程退出与外部超时。

Pass when恢复差异、stale binding、半加载状态都有可观测断言。

Stop：无法证明试点 invariants。

双轨 reconciliation

把现有配置作为 desired state；shadow 计算目标 fiber 集与顺序，先不执行。比对稳定后，再 canary 一个 realm / tenant。

Pass whenshadow 与现网装配一致，canary 可一键回旧路径。

Stop：出现无法解释的 nondeterminism。

最后才接 HMR

缓存失效、stale entry 检测与 fiber 重建必须包在事务边界；import 失败时恢复 module cache 与旧 fiber。

Pass when故障注入下不存在 half-reloaded state。

Stop：外部 emission 被错误纳入“事务回滚”承诺。

Risks & stop conditions

最大的风险不是 runtime 崩，
而是保证看起来成立。

形式结论依赖的纪律如果没有进入 API、测试与可观测性，就会退化成另一套手写 cleanup 约定。

R1 · Critical

Inverse 形式存在，语义错误

风险：runtime 不会自动证明 inverse witness；错误 inverse 会污染共享 context。
控制：原子 effect 契约测试、故障注入、state snapshot diff、幂等 teardown。
p.9–17

R2 · Critical

副作用绕过 Context

风险：全局变量、module-load side effect、直接 SDK 调用与外部写不在 accumulator 内。
控制：lint / review gate、capability interface、旁路访问 telemetry。
p.67–70

R3 · High

Independence 只是假设

风险：共享 key 或隐蔽状态让不同 fiber 的 transformation 不可交换，选择性恢复失效。
控制：key ownership、序列化 operation、显式 coeffect 排序。
p.22–27, p.43–45

R4 · High

依赖环让组件永久 inactive

风险：双方互相等待 satisfaction；这不是调度死锁，而是声明决定的不可达状态。
控制：加载前 cycle check，拆 core + integration component。
p.71

R5 · High

Interface drift / key collision

风险：key 匹配不代表类型或行为兼容，可能静默绑定错误 provider。
控制：namespace、版本范围、结构检查、contract test。
p.72

R6 · Medium

组件粒度爆炸

风险：为消除双向依赖引入 integration component，最坏可能 O(n²)，增加配置与认知成本。
控制：bundle、约定 wiring、codegen、粒度预算。
p.71

R7 · Medium

把 capability mediation 当 sandbox

风险：恶意代码可直接触底层 runtime object。
控制：不可信组件放进独立 runtime / process / container。
p.69–70

R8 · Unknown

收益被 runtime overhead 吃掉

风险：论文没有 benchmark，也没有 v4 生产对照。
控制：用现网负载测 transition latency、steady-state overhead、memory、恢复时延。
p.66–67

立即停止扩大迁移范围的条件

工程判断 试点组件仍有无法归属到 fiber 的共享写，或关键路径必须绕过 Context。

工程判断 故障注入出现恢复后状态差异、stale provider 引用或 half-reloaded state，且不能由明确边界解释。

工程判断 dependency graph 有无法通过业务拆分消除的 cycle，或 provider 兼容性无法在装配前判断。

工程判断 外部 emission 被产品要求承诺“自动回滚”，但业务没有 withholding、幂等或 compensation 方案。

工程判断 canary 的稳态开销、transition P99 或恢复时延超出团队预先写入 ADR 的预算；不要事后移动门槛。

工程判断 线上无法回答“哪个 fiber 因哪个 coeffect 被阻塞、当前 inverse depth、何时 quiescent”，先补 observability。

工程判断 迁移后的故障域反而从单组件扩大到共享 runtime，而 kill switch 不能在一个发布窗口内回旧路径。

工程判断 “继续投入，因为已经迁了一半”不是通过 Gate 的理由。最合理的终局可能是混合架构：容器负责强隔离与服务 rollout，时空组合 runtime 只治理少数高动态、长寿命的进程内组件，FRP 继续处理值级传播。
