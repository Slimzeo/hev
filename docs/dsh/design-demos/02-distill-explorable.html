Temporal × Spatial composability

可组合性，发生在时间与空间中 A Programming Paradigm for Spatiotemporal Composability

插件“能被加载”只是起点。真正困难的是：当组件在运行中交错进入、退出、替换时，系统如何只撤销它留下的变化，同时让依赖它的组件始终看到连贯的世界？

论文把答案拆成两条正交轴：以可逆 effect 管理时间，以响应式 coeffect 管理空间，再用生命周期 calculus 约束二者如何交错。

Research question → method → evidence

这篇论文为什么写，方法又凭什么有效？

研究问题：它不是解决“怎样加载一个插件”，而是解决同一长寿命进程中组件反复加入、退出、替换时的双重约束：离场组件只撤销自己的副作用；provider 出现、消失或换身份时，consumer 自动重解析并按正确顺序迁移生命周期。PDF p.4–6

既有瓶颈：restart/容器重建粒度过粗，手写 dispose 无法从安装动作结构化导出完整恢复，初始化期 DI 又不处理运行时 provider 变化和异步 teardown。单独“能卸载”或“能注入”都不完整。PDF p.4–8, p.17–22

  1. revertible effect：每次 change 同时返回 inverse，runtime 按 LIFO 组合。
  2. reactive coeffect：依赖 specification 把变化分类为 activating、deactivating、neutral。
  3. unified context + fiber calculus：四态与十条规则处理交错、撤出、异步和失败。
  4. Cordis：API、fiber 字段、loader 与 transactional HMR 给出可执行映射。PDF p.9–66

依据：第一层是形式定理——Table 1 穷举规则，Theorem 59/61/63/64/66/73 在显式条件下证明 preservation、recovery、ordering、coherence、progress、confluence；第二层是 Table 2 和 Algorithm 1–10 的构造对应；第三层是 Koishi 4000+ plugins 的存在性与采用度案例。PDF p.39–67

为什么可信：claim、状态空间、规则、前提与证明可定位，且定理量化任意合法 interleaving，不只是一条演示路径。
可信边界：runtime 不自动验证 inverse；independence、无环、有界、有限、total、no-failure 分别约束不同结论；外部 emission 不能倒带。论文无 benchmark，Koishi 用 Cordis v3，Agent Harness 是 p.79 future validation。

p.17–22coeffect specification 与 satisfaction

时间：不是“回到上一个快照”

一个 revertible effect 返回新状态与 inverse。多个 inverse 按 LIFO 组合，但 accumulator 属于具体 fiber，因此撤销目标组件时，可以只移除它的贡献，而保留独立组件已经写入的动作。

这比整棵系统做 snapshot rollback 更局部；也因此更苛刻：inverse 的 witness 必须由组件作者保证，runtime 并不会替你证明“这个 undo 真能复原”。

证据边界：论文的 recovery exactness 依赖 pairwise independence、正确 inverse 与 effect confinement。外部不可逆 emission、隐藏共享状态或错误补偿不在自动保证内。
p.9–17Def.1–19 · Thm.7 / 11 / 16 / 20

空间：依赖是一个持续变化的事实

coeffect 不是一次性的依赖注入。组件声明 specification；registry 的 committed view 变化后，resolution 也会变化。一次变化可被分类为 activating、deactivating 或 neutral，并驱动组件生命周期。

这解释了右侧实验里 chart 为什么可以“已注册但未激活”：组件身份存在，不代表依赖已经满足。provider 出现时，它不需要由业务代码手工寻找 load order。

p.45–47Thm.63 Ordering · Thm.64 Resolution coherence

calculus 真正承诺了什么

十条 lifecycle rule 把加载、卸载、依赖变更、迭代、异步与失败纳入同一个 operational semantics。由此可以讨论 preservation、recovery、ordering、progress 与 confluence，而不只是在实现里“希望它能工作”。

但这些不是无条件承诺：progress 需要 precedence acyclic 与 iterator 有界；confluence 还要求 quiescent、无 failed fiber、component 对其 provision total。
